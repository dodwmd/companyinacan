# Research and decisions (E24)

## How is the site published into the cluster?

Options: (a) ConfigMap with one file per key: keys cannot contain `/`, and the built site has `assets/`
and `.gz` siblings. (b) A PVC filled by a Job or `kubectl cp`: the can-static image is distroless (no
tar, no shell), so it needs another image or a sidecar. (c) A ConfigMap carrying one `site.tar.gz` plus an
init container that runs `can-static -extract`. **Chosen: (c).** The tarball is deterministic (sorted names,
zero mtimes, fixed gzip header), its sha256 is stamped into the pod template annotation, so a changed site
rolls the pod and an unchanged one does not. The ConfigMap is applied server-side so the object does not
carry a last-applied copy of its own data. Limit: 1 MiB per ConfigMap; `can up` refuses a site over 700 KiB
compressed (base64 overhead) with a message that names the cause. `extract` uses `os.Root`, refuses links,
devices, absolute paths and `..`, and caps the unpacked size at 64 MiB.

## How is the admin created without argv or a long-lived Secret?

`kubectl exec -i deploy/can-core -- /can-core admin bootstrap --username admin` with the password as the
first stdin line (the CLI already reads it that way). The TOTP secret is parsed from the command's
output. A Kubernetes Secret would be the alternative, but it would outlive the command. Resume: if the
account exists and its credentials were never shown, `reset-password --rotate-totp` re-issues both; once
shown (`launch.admin_creds_shown`), the account is never touched.

## Where does the /_forms route live?

The forms Service is in `mod-forms`; Traefik does not route across namespaces by default and the chart
leaves its own IngressRoute off (the module declares no subdomain). The route and its `stripPrefix`
Middleware are therefore applied into `mod-forms` after can-core has installed the module (poll for
`svc/forms`, bounded by the module timeout), with priority 100 against the site's 1.

## Images

- Release: `deploy/release-images.json` (`{"schema":1,"version":...,"images":{name:{ref}}}`), every ref
  `repo@sha256:<64 hex>`; generated by `scripts/gen-release-images.sh` from the digests the release
  pipeline pushed. Refused if a ref is a tag, a placeholder or malformed. The server pulls by digest.
- Dev from a checkout: `make images` -> `build/images/{can-core,can-static,can-forms}.tar` +
  `images.json` with the sha256 of each. `can up --images-from` re-verifies on read and after upload
  (`sha256sum` on the server) and imports with `k3s ctr -n k8s.io images import`; tarballs stay in
  k3s's `agent/images` directory so they survive a restart. Local tags (`can-core:dev`) are used; the
  forms image gets the exact `repository:tag` its chart expects.
- Giving both sources, or none (and no default manifest), fails before provisioning.

## Routing modes

https mode (sslip.io resolves and ACME limits allow): site on `<ip-dashed>.sslip.io`, admin on
`admin.<ip-dashed>.sslip.io`, `websecure` with the `letsencrypt` resolver. Fallback: plain HTTP on the IP,
catch-all site route, **no admin route** (reachable through `kubectl port-forward` only). The company domain
is added with TLS only when `dns.provider: cloudflare` (records created by can) or `--domain-live`; routing it
earlier would make Traefik request certificates for names that do not resolve and burn the Let's Encrypt
failed-validation limit.

## Backup and the kit

`can backup install` writes files locally; `launch` writes the same files over the host Runner (stdin
copies), then runs one script that installs restic if missing, initialises the repository and enables the
timer. Secrets are files, never script text. The restic password is generated per kit; on resume it is read
back from the host so the kit matches the repository. The kit is printed through `backup.PrintOnce`
(confirmation) or written with `backup.WriteKitFile` (refuses git trees). Without a terminal and without
`--print-secrets` / `--kit-out` the run refuses to start (nowhere to put the kit).

## Why a phase machine on top of idempotent applies

`kubectl apply` converges, so applies are simply re-run (this is how a changed company.yaml reaches the
cluster). Checkpoints exist for what is not idempotent or is expensive (images, admin, backup, kit) and
for `can status`. The `ready` checkpoint is cleared when a run starts, so an interrupted run is visible.

## CoreDNS restart

`coredns-custom` needs a CoreDNS restart to take effect. It is done only when `kubectl apply` reports that
ConfigMap as created or configured, not on every re-run.

## Alternatives rejected

- Embedding kustomize: not needed, `kubectl apply -f -` of the files named in `kustomization.yaml` suffices.
- A Job for the admin bootstrap: needs the same PVC (RWO) and a second SQLite writer; `exec` uses the running process's own mount.
- Installing kubectl for the operator: out of scope; the preflight says how.
