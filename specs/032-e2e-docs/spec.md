# Feature specification: End-to-end compose tests in CI and documentation refresh (Epic E23)

**Status**: built; the end-to-end suite passes locally (podman-compose 1.6.0, rootless Podman 6.1) and in the
advisory `e2e` workflow on Docker Engine 29.4.2 with Docker Compose v5.1.3. **Depends on**:
`specs/004-local-dev-cluster` (compose stack origin: `docs/local-compose.md`), `specs/016-module-wiring`,
`specs/023-work-ui`, `specs/026-people-ui`, `specs/027-jobs-ui`, `specs/018-equity`. **Principles**: constitution
III (test first), VI (open-source hygiene), VII (simplicity and measured claims).

## Why

Every module has unit and contract tests, but nothing proved that the shipped compose stack, through its public
edge, does what the documents say: a visitor's form becomes a lead, an administrator can log in with TOTP, a
second subject can approve an invoice, an unknown `Host` header reaches nothing, data survives a restart. The
documentation was also written before most modules existed: the README still called the project "pre-alpha" with a
`make enable crm` that is not a target, and there was no single place explaining the architecture or the known
security weaknesses.

## User stories

1. **A maintainer** runs `make e2e-up e2e` and in about a minute sees which end-to-end scenario broke and why, with
   a message that names the step.
2. **CI** runs the same suite on `ubuntu-latest` with the real Docker Compose, on pull requests that touch the
   stack, nightly and on demand, uploads service logs when it fails, and never blocks a merge (advisory).
3. **A newcomer** reads the README and learns what this is, what is verified and what is not, then follows
   `docs/getting-started.md` to a running stack, and finds every other document from `docs/index.md`.
4. **A reviewer** finds the known security weaknesses of the whole system in one list, each with its tracking
   issue or document.
5. **Every contributor**: a broken relative Markdown link fails a contract test.

## Requirements

### End-to-end suite (`test/e2e`)

- **FR-1** Go tests behind build tag `e2e` in `test/e2e`, helpers in `test/e2e/harness` (HTTP client, RFC 6238 TOTP,
  compose runner, JSON conveniences). Without the tag nothing needs a running stack.
- **FR-2** All traffic goes through the Caddy edge on `127.0.0.1:<port>` using virtual hosts (`*.localhost`), the way
  a browser or script would. The client dials the port directly, so no resolver support is needed.
- **FR-3** Scenarios, each independent and repeatable against the same stack (unique names, get-or-create for fixed
  identities): (a) site 200, contact form to a lead in the leads API, foreign origin refused; (b) admin login with
  password and TOTP, dashboard, audit, leads and token pages, logout; (c) work token mint, project and issue, UI
  sign-in, backlog, board; (d) people: 1:1 series, leave request submit and decision by a second identity, a
  colleague's 404, sensitive-field refusal, on-leave masking; (e) jobs: requisition, careers page with JobPosting
  JSON-LD, public application, recruiter UI shows the candidate, interviewer blindness; (f) finance: party, invoice,
  creator refused, approval by a second subject, send, public link 200, payment, paid; (g) equity: draft, submit,
  wrong approvers refused, board approval, activate, vesting; (h) every module refuses no token and every other
  module's token (401), hostile `Host` reaches nothing private, no metrics or debug endpoints, anonymous callers
  refused; (i) `down` without `-v` and `up`, then all of the above data and the admin login are intact.
- **FR-4** Clear failure messages: each assertion names the step and the expected and actual HTTP status and a
  prefix of the body. A global timeout (`-timeout 15m` in `make e2e`) bounds the run; `TestMain` fails fast with
  a pointer to `make e2e-up` when the edge does not answer within 90 seconds.
- **FR-5** Makefile targets `e2e-up`, `e2e`, `e2e-down` (and `docs-check`); the compose project is `can-e2e`
  so it never touches other projects' containers.

### Compose changes the suite needs

- **FR-6** `equity` joins the compose stack (it was missing): image target, config, public dev token, keyring
  generated by `init`, edge host `equity.localhost`.
- **FR-7** A catch-all edge block answers an unknown `Host` with `421`. (The documentation claimed such requests were
  served from the public site; they received an empty `200`.)
- **FR-8** An overlay `dev/compose/e2e.yml` adds **introstub**, a fake token-introspection service with five public
  fake identities, and points `people` and `equity` at it, so the suite can act as HR, a manager, two employees and
  a board member. It is test infrastructure, absent from the base stack and from every release.

### CI

- **FR-9** `.github/workflows/e2e.yml`: not required, `continue-on-error`, triggers `pull_request` (path filtered),
  nightly `schedule` and `workflow_dispatch`; actions pinned by SHA, `permissions: contents: read`,
  `persist-credentials: false`; uploads service logs on failure; always tears down. `test/contract` asserts these
  properties and that it is not a required check.

### Documentation

- **FR-10** README rewritten: what it is, honest status (pre-release, nothing run on a real server), module table
  with status, architecture sketch, quick start, clients, what is verified, footprint measured against claimed with
  sources, security posture, contributing, licence.
- **FR-11** New `docs/getting-started.md` (compose, k3d, real server with caveats), `docs/architecture.md` (with
  sequence diagrams for lead capture, hire handoff, approval flow), `docs/security-model.md` (trust boundaries,
  tokens, sealed data, audit, consolidated residual risks), `docs/index.md` (entry).
- **FR-12** `scripts/check-doc-links.sh` and a contract test: every relative Markdown link resolves, offline.
- **FR-13** `SPEC.md` is changed only where it contradicted the implementation (listed in the pull request);
  `docs/epics/README.md` statuses corrected and E23 added.

## Non-goals and known gaps (stated, not hidden)

- Personal access tokens issued in the admin UI cannot be tested through compose: can-core runs with
  `CAN_INSTALLER=none`, which leaves module management (catalogue, PATs) off, and the fake TokenReview cannot
  register module tokens. The suite asserts the limitation and uses module-minted service tokens instead. Issue #43.
- The compose stack has no Kubernetes: TokenReview, NetworkPolicy, admission policy, TLS, backups and cluster
  install of modules are not covered. The `dev-cluster` workflow covers part of that for `work`.
- Cross-module flows that need can-core to route events (lead to inbox, hire to onboarding, approvals) are not in the
  compose suite; `test/wiring` covers them in process.
- Browser behaviour (JavaScript, CSS, accessibility, PWA install, Web Push) is not tested.
- The suite is advisory and slow to start (an image build of a few minutes); it is not a required check.
