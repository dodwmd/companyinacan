# Research and decisions (E03c)

**R1 Personal access tokens vs SSO sessions.** No SSO exists yet (E11 backlog). A token is a random
256-bit value with the prefix `canpat_`; only its SHA-256 is stored (a fast hash is enough for a
random 256-bit secret, and lookup is by hash). Alternatives rejected: signed self-contained tokens
(cannot be revoked without a list anyway, and put claims where modules could trust a stale copy);
reusing the admin session cookie (CSRF-bound, not for scripts).

**R2 Who the token acts as.** The issuing administrator: subject `user:<username>`, the same subject
RBAC and approvals use. A token can grant only permissions the issuer holds (checked at issue through
`rbac.Check`) and only permissions the module's manifest declares; permissions removed from a manifest
later are dropped at introspection. List and revoke are own-only unless the caller holds `rbac.manage`.
A foreign token answers 404 on revoke, like an unknown one.

**R3 Introspection answers.** Extends `POST /v1/tokens/introspect`: a `canpat_` token is answered
before any TokenReview (so it never counts against the review rate limit) and only to the module it is
bound to; unknown, expired, revoked, malformed, wrong audience and another module's token produce the
identical `{"active": false}`. A module token still goes through TokenReview. The module side sends
`audience` (its own id) as a second guard.

**R4 Module-side cache.** Positive answers 30 s (never beyond the token's own expiry), negative 5 s,
errors never cached, one in-flight call per token, 1,024 entries, keyed by the SHA-256 of the token.
Consequence, stated in the docs: revocation reaches a module within 30 s. Valid tokens are never rate
limited by this code; the existing per-module failure limiters count only failures.

**R5 Which tokens a module asks about.** Only tokens shaped like `canpat_` plus URL-safe base64, at most
128 characters. Everything else is refused locally, so garbage cannot become calls to can-core.

**R6 Secrets.** Generated by can-core into the module's `can-module` Secret (already on the installer's
allowlist, already `envFrom` into every container), because the installer refuses any other Secret name
and a per-module Secret would need a new allowlist entry. `generatedSecrets` keeps an existing value
and only creates a missing one, so enabling twice, upgrading and disable/enable never change a
credential. The key list is a table (`core/server/modsecrets`) rather than a manifest field, to avoid a
schema change for something only the in-house modules need. The sealed-field keyring is added to by a
rotation (`k<N+1>` first, old keys kept) so existing data stays readable until the module's own
`rotate-keys` re-seals it. `CAN_JOBS_HASH_KEY` is never rotatable: a new key silently splits every
candidate from their duplicates. Alternative rejected: rotating by deleting the Secret (loses the
keyring and with it the data).

**R7 Rolling on change.** Environment variables are read at process start, so a changed Secret would
not take effect. The installer stamps `can.dev/secret-version` (16 hex characters of a SHA-256 over the
Secret data) on Deployment and StatefulSet pod templates; unchanged secrets produce an unchanged
template and no restart. Jobs and CronJobs are not stamped (a Job's template is immutable). If the
rollout fails and is rolled back, the Secret already holds the new values while the old pods keep
running with the old ones until the next successful enable; the module works in both states.

**R8 Rotation requests.** `can-core admin secrets rotate` writes a row (audited, no value) because the
CLI runs in the pod without Kubernetes credentials of its own; the reconciler reads pending rows,
treats them as an upgrade, and clears them only after a successful install. `CAN_WEBHOOK_SECRET`
rotation generates a new HMAC secret that is recorded only if the install succeeds.

**R9 Publishing through can-core.** `POST /v1/events` gains an optional `source_id`; a repeat of the same
(module, source_id) returns the first event and delivers nothing. Modules use their outbox envelope id.
The key table is pruned after 7 days. Modules keep their own outbox, so can-core being down only delays
events (forms is the exception, see below). The old `webhook.url` direct path remains for standalone use.

**R10 Receiving.** `modclient.Receiver` verifies `X-Can-Signature` (HMAC-SHA256 of timestamp and body
with the module's `CAN_WEBHOOK_SECRET`) and a 5-minute replay window before parsing, bounds the body,
drops redelivered ids (bounded set), answers 5xx on a handler failure so can-core retries. The endpoint
is `/v1/can/events` on the module's existing listener; the signature, not a token, is the
authentication. A secret shorter than 16 characters refuses everything.

**R11 Approvals.** Jobs: `CoreApprover` implements the existing `Approver`; the requester must be a
person (`user:<name>`), because the engine's separation of duties needs an identity; the bootstrap token
cannot ask. Finance: the existing `Approver` is a synchronous yes/no per approver, the engine is
asynchronous, so the engine's decision is stored (`core_approvals`) and `CanApprove` consults it,
bound to the invoice version and refusing the requester. The two-step flow (engine decides, then a
`finance.approve` holder calls approve) is kept because approval writes `approved_by` and numbers the
invoice, which needs a principal. Only invoices are wired; the other kinds keep the permission rule.
Defence in depth: both modules record a decision as rejected if can-core lists the requester among the
approvers.

**R12 The store has one connection.** A query on `s.db` while a transaction is open waits forever. The
finance `CanApprove` runs inside the approval transaction, so it reads through that transaction (passed
in the context). A hang found in testing, kept as a test.

**R13 Data minimisation in events.** can-core keeps events 30 days and feeds notifications. forms'
`lead.created.v1` through can-core carries ids only (`fields` is required by the schema and is empty);
the lead is read through the `leads` capability. people's hand-off from jobs carries no personal data
either, so the person is a placeholder ("New hire" and the candidate id) for HR to complete; fetching
the real name from the `ats` capability needs a token that may read it and is left out. work's
event payloads (issue key, title, priority, status, reporter, assignee) are unchanged; the title is
business content, listed in the module's data classes.

**R14 Charts.** Modelled on the starter module charts and rendered by the installer's own subset
renderer; configuration is a ConfigMap built from `values.yaml` (strict loaders, so only keys each
module accepts), secrets only through `can-module`. The keyring is a `subPath` mount of one key of
`can-module`, mounted 0440 with `fsGroup`: the module loaders were changed to accept that mode (not
group-writable, not other-readable) because a non-root pod cannot read a root-owned 0400 file.
`settings` in company.yaml are not mapped onto the chart's `config:` block (no `values.tmpl.yaml`).

**R15 Forms exposure.** The installer allows an IngressRoute only for `<subdomain>.<domain>`. forms'
public listener is designed as a same-origin path (`/_forms`) of the company site, which the installer
cannot route, so the chart's ingress is off. Unresolved here: either a `forms.<domain>` host with CORS,
or an installer rule for a path route on the apex host.

**R16 CI.** The existing advisory job already builds can-core and creates the cluster; it now also builds
the `work` image (resolving the base image digests of the current tags), imports it, and the
integration test installs `work` from the repository's real `modules/` directory. It runs only when
`CAN_IT_WORK=1`.
