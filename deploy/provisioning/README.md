# deploy/provisioning

Container build for the identity provisioning module (`cmd/can-provision`).

## Image

`Dockerfile` is a two-stage build: `golang` builder, then `gcr.io/distroless/static-debian12:nonroot`
(no shell, no package manager, uid 65532). The binary is static (`CGO_ENABLED=0`; SQLite is the
pure-Go `modernc.org/sqlite`). Because there is no `curl`, health probes use the binary itself:
`/can-provision healthcheck -addr 127.0.0.1:8090`.

## Digest pinning

Both base images must be pinned by digest before a release build. The Dockerfile ships with
placeholders (`sha256:REPLACE_WITH_...`) so an unpinned build fails instead of silently using
a moving tag. Look the digests up, review them, and pass them as build args (or commit them):

```sh
crane digest golang:1.27                          # GO_IMAGE_DIGEST
crane digest gcr.io/distroless/static-debian12:nonroot   # DISTROLESS_DIGEST
```

## Runtime contract

| What | Value |
|---|---|
| Listener | `:8090`: the SCIM server under `/scim/v2` (its own bearer tokens) and the provisioning API under `/v1/provision` (bearer token). Expose only `/scim/v2` through the ingress; `/v1` stays ClusterIP. `GET /healthz` needs no token |
| Data | `/data/provision.db` (SQLite, WAL), one persistent volume |
| Config | `/etc/can-provisioning-config/provisioning.yaml` (`CAN_PROVISIONING_CONFIG`); see `modules/provisioning/chart/values.yaml` |
| Secrets | env `CAN_PROVISIONING_API_TOKEN` (24+ characters, generated by can-core), `CAN_WEBHOOK_SECRET` (16+, can-core), `CAN_PROVISIONING_DIRECTORY_TOKEN` (a people token with `people.read` and `people.write`) and one env var per connector credential (`token_env`, `secret_env` in the config) |
| Idle RAM | measured locally, see `specs/028-identity-provision/research.md` R9; target 20 MB, limit 64 MB |
| Root filesystem | read-only works: only `/data` is written |

SIGTERM triggers a graceful shutdown within 20 seconds; set `terminationGracePeriodSeconds` to at
least 30. Runs are state in SQLite, so a restart resumes them, and queued events are in the SQLite
outbox.

The image has **not** been built in CI or run on a cluster; the Dockerfile is a fragment with digest
placeholders, and `scripts/check-image-pins.sh` fails a release build until they are pinned.
